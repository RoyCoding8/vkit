# Scheduling facts from a captured Perfetto trace

`explain_trace_interval(root, path, start_ns, end_ns, tid, upid=None, timeout_seconds=30)` captures one repository-local native Perfetto trace and analyzes one half-open interval `[start_ns, end_ns)` on Trace Processor's normalized trace timeline. Bounds are integer nanoseconds inside `[-2^61, 2^61]`; the interval must be at most one hour and inside the trace bounds. Trace bounds and scheduler rows outside that conservative range, invalid negative durations, or inconsistent integer aggregates produce `UNKNOWN` rather than potentially rounded nanosecond totals. `tid` is the operating-system thread ID recorded in the trace; when that ID appears under multiple trace-local process IDs, pass the `upid` returned by Perfetto to disambiguate it.

The operation uses fixed queries against Perfetto's `thread`, `trace_bounds`, `thread_state`, and `stats` tables. It does not accept SQL. It clips each thread-state row to the requested interval and reports exact state totals, a sample of at most 100 observed segments (including recorded CPU, I/O-wait, blocked-function, and waker fields), unobserved and overlapping nanoseconds, and nonzero data-loss statistics. `MEASURED` means the supplied trace covered the full interval without reported data loss or overlapping rows. `INCOMPLETE` preserves the observed facts but reports gaps, overlaps, or loss. `UNSUPPORTED` means the trace has no usable bounds, matching thread, or scheduler states. `UNKNOWN` means the bounded engine could not finish or return a valid result. `UNAVAILABLE` means the pinned package/binary is absent or could not be launched.

The trace is captured into a private temporary file, limited to 32 MiB, and analyzed in a fresh isolated Python process under a hard wall deadline. SQL aggregates every matching state row; the response samples at most 100 events, records at most 128 loss rows, and is limited to 2 MiB of JSON. The optional engine is `perfetto==0.58.2`, whose package manifest pins the Trace Processor shell binary by version, size, and SHA-256. The request path only checks the existing SHA-named cache entry and rehashes it; it never downloads an engine. Installation or CI setup must prefetch the package-pinned binary before calling the operation, for example:

```powershell
uv run --extra engines python -c "from perfetto.prebuilts.manifests.trace_processor_shell import TRACE_PROCESSOR_SHELL_MANIFEST; from perfetto.prebuilts.perfetto_prebuilts import get_perfetto_prebuilt; print(get_perfetto_prebuilt(TRACE_PROCESSOR_SHELL_MANIFEST))"
```

That setup command may download the official release binary. The analysis call itself does not use the network. On Windows the worker runs inside a kill-on-close Job Object; on POSIX it runs in a fresh process group, so a timeout also stops the Trace Processor child.

The tests construct a tiny native ftrace protobuf trace from Perfetto's public `Trace`, `TracePacket`, `FtraceEventBundle`, `FtraceEvent`, and `SchedSwitchFtraceEvent` schema. The fixture has four scheduler switches and an optional `lost_events` marker; tests load it through the pinned native processor and check exact clipped totals and the emitted loss statistic. See [Trace Processor](https://perfetto.dev/docs/analysis/trace-processor-python), [TracePacket schema](https://perfetto.dev/docs/reference/trace-packet-proto), [scheduler blockage analysis](https://perfetto.dev/docs/case-studies/scheduling-blockages), and [trace data loss](https://perfetto.dev/docs/concepts/buffers).

These are observations in the selected recording. A no-loss statistic does not prove that the recorder captured every relevant event. Trace Processor maps clocks onto its normalized timeline; this operation does not independently prove synchronization among source clocks. State overlap or temporal order does not establish causality or a root cause, and the result says nothing about executions outside this trace.
