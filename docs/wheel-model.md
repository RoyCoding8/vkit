# Python wheel install mapping

`compare_wheels(before, after)` checks two repository-local `.whl` archives against the fixed `python-wheel-install-map-v1` profile. It validates the wheel filename and `WHEEL`/`METADATA` headers, verifies the `RECORD` path, digest, and size for each archived file, and compares normalized install targets, payload bytes, executable bits, and install-affecting metadata. It also returns distribution metadata, supported tags, declared and inferred import roots, and entry points.

The operation reads archive members without extracting them. It does not install wheels, import package code, run build hooks, or invoke entry points. `SAME_INSTALL_MAPPING` means the supported normalized scheme-qualified paths, bytes, executable bits, and compared metadata match. `DIFFERENT_INSTALL_MAPPING` returns the differing paths or metadata fields. `UNSUPPORTED` means the archive is malformed, nonportable, or uses install behavior outside this profile. `UNAVAILABLE` means the exact `packaging==26.3` engine pin is absent. `UNKNOWN` means an I/O or archive read failed before comparison completed, or supported evidence would exceed the 2 MiB serialized-output limit; in that case, no difference count or partial result is reported.

The profile accepts at most 64 MiB per compressed archive, 20,000 ZIP entries, 64 MiB per expanded member, 256 MiB total expanded bytes, and a 100:1 expansion ratio. It accepts stored and deflated members, ordinary files and directories, SHA-256/SHA-384/SHA-512 `RECORD` hashes, and the `purelib`, `platlib`, `headers`, and `data` install schemes. It requires `WHEEL`'s `Generator`, validates an optional `Build` field against the filename, and accepts core metadata versions 1.1, 1.2, and 2.1 through 2.6. Filename tags and aggregate expanded `WHEEL` tags are each capped at 512 before parsing. It rejects unsafe, nonportable, case-colliding, or file/directory-prefix-colliding paths, symlinks, signatures, scripts requiring shebang rewriting, unknown schemes, malformed metadata, and unmodeled ZIP compression. It reports at most 256 differences, 128 inferred import roots, 8 paths per root, and 512 metadata list items; each truncated inventory reports its total count.

The comparison ignores ZIP timestamps, member ordering, and compression choices. It canonicalizes the installed `RECORD` rows after mapping `.data` files to their target schemes. Scheme labels are abstract namespaces; for example, `purelib` and `platlib` may alias on a real host, so this operation does not claim that a concrete installer would produce two distinct physical directories. It does not predict collisions with another installed distribution and does not establish that any inferred import root imports successfully on a target interpreter.

The wheel archive follows the [Python binary distribution format](https://packaging.python.org/en/latest/specifications/binary-distribution-format/), and its METADATA follows the [core metadata specification](https://packaging.python.org/en/latest/specifications/core-metadata/). Filename and requirement parsing use the project-pinned `packaging==26.3` dependency.

## Approved build checks

An optional `kind: "build"` check runs through the ordinary manifest digest approval, runner, and run-record path. It fixes the uv executable path, version and SHA-256; the active Python version and executable SHA-256; a captured build-constraints lock; a captured local wheelhouse; a captured runtime requirements lock; and literal module imports and installed console-entry-point outcomes. These declarations are part of the accepted check definition. The `inputs` must cover the project files used for packaging and every file in the three profile inputs.

The worker copies the captured input snapshot into two new source directories. It invokes the pinned uv executable twice with independent temporary build caches, an explicit Python interpreter, `--no-index`, `--offline`, `--find-links`, and `--require-hashes`. Build constraints must pin and hash the complete build-backend dependency closure. Each subprocess shares a 256 KiB stdout/stderr capture budget. The supervisor drains both streams to the run logs and kills the process tree if the combined limit is exceeded. The report retains both wheel files and bounded output evidence. A nonzero backend build is `BLOCKED`: it records an execution observation and does not call the package defective. Successful builds compare the wheel bytes and filenames exactly.

Each wheel is installed in its own clean uv-created virtual environment. The captured hashed runtime lock supplies dependencies from the same wheelhouse; the project wheel is then installed without dependency resolution. `pip check` confirms the lock closes the wheel metadata requirements. The worker imports each named module under `python -I` and checks that the module loaded from the clean environment. Each declared entry point runs with its literal argument vector and must match its expected exit code, stdout, and stderr byte-for-byte. A completed assertion mismatch is `FAIL`; missing or mismatched toolchain, incomplete captured inputs, timeouts, backend/setup errors, or malformed reports are `BLOCKED`.

`PASS` means these two builds on this host and the declared interpreter/uv/backend profile produced identical wheel bytes, and both wheel installs met the listed import and entry-point assertions. It is not cross-host reproducibility, an OS sandbox, a universal dependency-resolution proof, or a claim about unlisted imports and entry points. Build backends and installed package code execute as part of an explicitly accepted check; `cwd` alone is not an isolation boundary. The operation is optional and does not enter any mandatory gate unless an owner explicitly adds and accepts the check.
